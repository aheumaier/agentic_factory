The scope matches the approved Input. I found no scope creep: the ceiling-outcome machinery in FR-012..FR-016 and the report rows in FR-010/FR-011 are needed to deliver it.

The spec is **not ready for /speckit-plan**. Two of the facts it is built on are wrong:
- A session that hits a limit does not "end silently". It raises an error.
- The writer's tools are not limited to six.

The ceiling outcome is also not specified well enough at three points: where it meets seat classification, the workflow's final failure, and the retry mode. All the fixes are edits to the spec text. None changes the Input.

SDK caveat: I read the SDK installed in the main checkout, version 0.2.150. The worktree's `harness/swe-agent/uv.lock` pins 0.2.165, and `sandbox/swe-agent/Dockerfile:27` installs `claude-agent-sdk>=0.2.152` with no upper bound. The SDK behaviour cited below is confirmed on 0.2.150 only.

## Findings (most severe first)

- **[High] The preamble's "a limit stop ends silently" is wrong, and a ceiling stop can be misread as a seat outcome.** Spec lines 24-26; checklist note 2 (lines 41-46) repeats the claim.
  - Problem: the claim is false. When a session hits `max_turns` or `max_budget_usd`, the CLI sends an `is_error` result with subtype `error_max_turns` or `error_max_budget_usd`. The SDK then raises `ResultError` (`claude_agent_sdk/_internal/query.py:405-420`; `_errors.py:56`, whose docstring uses `e.subtype == "error_max_turns"` as its example).
  - Today, without a seat, that error escapes `run_implement` (`agent.py:340-376`) and `main` (`agent.py:553-576`), so the run exits 1 with a traceback. On a seat, `guarded_query` catches it first (`seat_guard.py:150-160`). `classify_result_error` (`seat_guard.py:100-109`) looks only at `api_error_status` and the result text, using `_EXHAUSTED_RE = rate.?limit|usage limit|limit reached|quota` (line 38).
  - Scenario (plausible): a max-turns result whose text contains "limit reached" is classified as `SeatExhausted`. The run exits 75, the workflow hands off to another seat without charging a Build attempt, and the seat is wrongly marked exhausted. The loop repeats until `MAX_SEAT_HANDOFFS`, which defeats FR-013 and SC-004. If the text does not match, the run exits 1. In per-task mode `checkpointer.finish` and the push are skipped, and today's plain-failure path fails the whole run.
  - Fix: correct the preamble and checklist note 2. Today a limit stop raises an error that exits 1, or may be misread as a seat outcome. Add an FR: "A ceiling stop MUST be recognised by the session result's subtype, whether it arrives as a result message or as the SDK's result error, and before any seat classification. A test MUST show that a ceiling result whose text matches the seat-exhausted pattern is never reported as a seat outcome."
  - Placement: `seat_guard.py` is a byte-for-byte copy shared with architect-agent (`seat_guard.py:17-19`, enforced by `tests/test_seat_guard.py`). The spec should say either that the shared module gets the subtype check (architect-agent's copy then changes too, which is harmless) or that agent.py checks around the stream.
  - Effort: hours. Confirmed (SDK path, code path). The regex misclassification is Plausible; it depends on the exact result text.

- **[High] The writer's tool set is wrong, which undermines FR-002 and the explorer-off arm of SC-007.** Spec lines 30-31, FR-002 (line 202), SC-001, SC-007.
  - Problem: `build_options` (`agent.py:317-337`) sets `allowed_tools=[...six...]` and `permission_mode="bypassPermissions"`, but does not set `tools`. In the SDK, `tools` is the base set offered to the model and `allowed_tools` only auto-approves (`types.py:1944` vs `:1955`; `subprocess_cli.py:586-604` maps them to `--tools` and `--allowedTools`). The writer therefore has the CLI's full default set today, including the Agent/Task tool and WebFetch. Confirmed.
  - It follows that the writer can already start built-in subagents, for example general-purpose, which can write files. Plausible: I have not seen an init message. So "the writer stays the only session that changes files" (FR-002) is not guaranteed. The explorer-off arm of SC-007 is "built-in subagents available", not "no subagent". SC-001 says nothing about other subagents.
  - Scenario: with the explorer on, the writer starts general-purpose instead of the explorer. Files change outside the writer, and the A/B comparison measures something other than what it claims.
  - Fix: correct lines 30-31. Add to FR-002: "Offered tools are set explicitly. The writer MAY start only the explorer; built-in subagents are not offered." Require the measurement (FR-018) to record the offered tools and agents for each arm, taken from the session's init message.
  - Effort: hours. Confirmed (tools/allowed_tools semantics). Plausible (built-in agents present and able to write).

- **[High] FR-014's "the same way as Eval-Gate failures" is undefined when the last attempt has no gate result.** FR-014 (line 233), FR-013.
  - Problem: the Build loop (`pipeline_workflow.py:319-360`) has no handling around Build. Its final failure is `raise ApplicationError(f"... {eval_result['reason']}")`, and `eval_result` starts as `{}`. A ceiling attempt skips the gate, so it has no `reason`.
  - Scenario (illustration, Plausible): every attempt ends on a ceiling stop. A plan that reuses the existing raise reads `eval_result['reason']`, raises `KeyError` inside workflow code, and the workflow task retries forever. The run hangs instead of failing.
  - Second problem: `FEEDBACK_PROMPT_SUFFIX` (`agent.py:73-78`) hardcodes "The previous attempt on this branch failed the Eval-Gate". A ceiling note would reach the model labelled as a gate failure.
  - Fix: add to FR-013/FR-014 that a ceiling attempt does not run the Eval-Gate and has no gate result (spec 015 FR-022's result document is absent for that attempt). The final failure names the last attempt's outcome of either kind, with an error type the operator can tell apart from a gate failure. The feedback wording names its source (gate or ceiling), and that change to the feedback suffix is allowed. FR-006 bars only IMPLEMENT_PROMPT/TASK_PROMPT text, so say so explicitly.
  - Effort: hours (spec), hours (code). Confirmed (loop shape, suffix). Plausible (the hang, which depends on the plan).

- **[High] FR-015 silently changes spec 018 FR-014 and FR-012, and its "one model turn" bound is wrong.** FR-015 (lines 235-237), "Changes to other specs".
  - Problem 1: 018 FR-014 stops Build after the session that reaches the remaining cap. FR-015 moves the stop inside the session via `max_budget_usd`, a different mechanism and moment.
  - Problem 2: `max_budget_usd` runs on the SDK's own cost figure (`types.py:2021`, "stop if this budget is exceeded"). 018 FR-012 says the provider's cost figure MUST NOT replace the price table.
  - Problem 3: the stop happens only after the budget is exceeded. An explorer call is one writer turn but many inner turns. The overrun is therefore at least one writer turn including any explorer call, not "one model turn".
  - Problem 4: per-task sessions all run inside one Build activity. The remaining cap must be recomputed before each session, not once at attempt start as 018 FR-014 states.
  - Scenario: the SDK's cost and the price table differ, so the in-session stop and the ledger disagree on whether the cap was reached. The run then gets a budget stop that the ledger says is under the cap, or the reverse.
  - Fix: list both changes under "Changes to other specs" (018 FR-014 gets an in-session stop, recomputed per session; 018 FR-012 gets "SDK cost used only as a stop trigger, ledger cost stays price-table"). Replace "one model turn" with "one writer turn, including any explorer call within it". Define the tie (ceiling equals remaining cap) as 018's budget stop. Say that a ceiling-stopped session's usage is complete, because its result arrives, so it is not "incomplete" under 018 FR-011.
  - Effort: hours (spec, needs 018's owner). Confirmed.
  - Conflicts with: spec 018 FR-012, FR-014. These are not reversed, but they are amended without being named.

- **[Medium] A ceiling retry runs as one session over all remaining tasks.** FR-013, SC-003, Assumption at line 297.
  - Problem: `run` (`agent.py:492-533`) uses per-task mode only when `feedback is None` and there is one task file. A ceiling retry carries feedback, so it runs as a single `/speckit-implement` session over every remaining task.
  - Scenario: task T007 hits the per-task turn ceiling of 120. Attempt 2 runs T007..T020 in one whole-attempt session under a different ceiling kind. That is the large-session pattern specs/011 F7-a removed. SC-003's "next attempt" is measured under a different ceiling than the one that stopped. If T007 is hard, three ceiling stops use all three attempts and give the model nothing new beyond the ceiling note.
  - Charging one attempt per ceiling stop is coherent otherwise. It bounds the run, and 018's budget stop covers cost separately.
  - Fix: the spec must choose. Option (a): a ceiling note is not Gate feedback, so a ceiling retry with one task file and ID-carrying tasks keeps per-task mode, starting at the stopped task. Spec text: "the retry trigger is not the `feedback` argument". Option (b): keep today's single-session retry, state the consequence, and say SC-003 measures the whole-attempt ceiling on the retry.
  - Effort: hours. Confirmed.
  - Conflicts with: specs/011 FR-026 (line 235) and F7-a (line 44), "the single-session Gate-feedback retry stay[s]". Option (a) does not contradict FR-026's wording if the spec defines a ceiling retry as a separate case, but it must say so.

- **[Medium] FR-012's commit and output order differ from the seat path.** FR-012 (lines 226-229).
  - Problem 1: the seat path (`agent.py:519-522`) calls `checkpointer()`, which commits only when the done-task set grows (`agent.py:268-278`), then `checkpoint_push`. It does not commit unticked edits. FR-012 commits leftover edits, which is the `finish()` behaviour (`agent.py:280-285`). Two stop paths would then leave the branch in different states for no stated reason.
  - Problem 2: "Its last output line MUST name the ceiling" conflicts with the stdout protocol. `seat_status` is the last line on 75/77 and second to last on success. `_with_seat` releases a seat with `None` usage on any non-seat error (`pipeline_workflow.py:142`), so a ceiling stop would lose the seat's usage reading.
  - Fix: say why a ceiling stop commits leftovers when a seat stop does not, or align the two. Require the ceiling outcome to carry the `seat_status` usage, define the line order (for example ceiling line, then seat_status last, matching 75/77), and map it in `run_swe_agent_activity` (`activities.py:244-305`, where every other non-zero exit becomes `RuntimeError`) to a typed, non-retryable ApplicationError. Name a single place where exit codes are assigned, shared with 018's budget stop, for example the seat-guard/agent protocol contract.
  - Effort: hours. Confirmed.

- **[Medium] FR-017/US4 asks for evidence the run record cannot hold, and US4's reason contradicts spec 019.** US4 AS1 (line 147), FR-017 (lines 242-243), line 139.
  - Problem 1: "the run's record shows evidence that the session received the marker". 018 FR-004 bars model text from the record. Asking the model to confirm would need prompt text, which FR-006 bars.
  - Problem 2: line 139 says 019's lessons depend on CLAUDE.md reaching the agent. 019 FR-021 delivers lessons "near the start of its prompt" and MUST NOT rely on the agent loading repo settings.
  - Background: with `setting_sources=None` and no `skills`, the SDK sends no `--setting-sources` flag (`subprocess_cli.py:719-720`: `if effective_setting_sources is not None: cmd.append(...)`). The `["user","project"]` default applies only when `skills` is set (lines 556-557). So the CLI default decides whether CLAUDE.md loads. pm-agent passes `setting_sources=[]` explicitly to turn it off, which supports reading "None means the CLI default", but the CLI version decides that default.
  - Scenario: the live check passes or fails for a reason nobody can show, because there is nothing observable to record.
  - Fix: make the marker an instruction with an effect you can see, for example "add the trailer `Marker: <id>` to commit messages" or "create file X", and check for it in git. Record the result, date and SDK/CLI version in the spec directory, not in the run record. Change line 139 to "any target repo's own rules depend on this. 019's lessons do not (019 FR-021)."
  - Effort: hours. Confirmed.
  - Conflicts with: spec 019 FR-021 (the claim only, not the design).

- **[Medium] SC-007/FR-018 do not measure what they claim.** SC-007 (line 287), FR-018 (line 250), FR-007 (line 212).
  - Problem 1: "the writer's context tokens" is not defined. With the explorer on the writer's model, `model_usage` cannot split writer from explorer. Separating them needs `parent_tool_use_id` on assistant messages, or the TaskStarted/TaskProgress/TaskNotification usage messages. FR-007's "explorer's share on its own" needs the same.
  - Problem 2: 5-10 tasks cannot reliably detect a 20% median shift or a gate-pass-rate difference.
  - Problem 3: FR-018's "does not lower" conflicts with SC-007's 20% threshold.
  - Problem 4: the measurement is confounded with spec 021's own measurement (021 FR-022) and with 021's index tools on the writer (021 FR-018).
  - Fix: define the metric as the peak input context of main-thread (no parent tool use) assistant turns per task. Pair the arms on the same tasks and report per-task differences. Make one sentence the keep rule (SC-007's). Fix the index-tool state per arm, and record it in the measurement.
  - Effort: hours. Confirmed (SDK fields). Plausible (power).

FR-010's turn count does not say whether explorer turns (bounded by `AgentDefinition.maxTurns`, FR-005) are included.

- **[Low] The explorer's tools vs 021's index tools, lessons, and answer cutting are not specified.** FR-001, FR-003, FR-004.
  - Problem: 021 FR-018 gives the index tools to the writer, but the explorer's list is fixed to Read/Grep/Glob, and FR-003's "what is where" is exactly what the index serves. 019 sends lessons to "any model-calling stage added later", but the spec doesn't say whether the explorer is one. FR-004's cut has no enforcer, because the SDK has no subagent output cap. A hook on the Agent tool's result is needed, or SC-002 can't be enforced.

- **[Low] Temporal determinism and rollout order are not stated.** "Changes to other specs" / Assumptions.
  - Answer to the patch question: a new `except` branch for a new ApplicationError type around the Build call needs no `workflow.patched` ID, because old histories never contain that error type. A new activity, timer or command before Build (for example to fetch ceilings or the remaining cap) does need one. "How ceilings reach the sandbox" is left to the plan, so it is open.
  - Rollout: if the image emits the new exit code before the worker maps it, the run gets today's `RuntimeError`. That is safe because ceilings default to off.
  - Fix: "A patch ID is required if the plan adds a workflow command, per repo convention (`seat-pool-v1` and others). Deploy the worker mapping before the image. In-flight runs keep today's behaviour."
  - Effort: minutes. Confirmed.
