## Summary
I reviewed `specs/021-code-index/spec.md` and `checklists/requirements.md` in the worktree `/Users/aheumaier/Codebox/agentic_factory/.claude/worktrees/021-code-index`. I checked them against the harness agents, the workflow and its activities, the installed SDK's CLI flag mapping, the registry SKILL.md files, `docs/agent-factory-architecture.md`, and the specs 018, 019 and 022 in their worktrees. I edited nothing.

The spec matches the operator's Input point by point, and its stated facts about the code check out. It is not ready for `/speckit-plan`. Four contracts are missing that the plan cannot settle on its own:
- which commit a stage is pinned to;
- what "stale" means;
- where `repo_map` gets its seed paths;
- where the measurement data comes from.

One requirement (FR-019, no prompt text) clashes with prompt text that already exists. The checklist's "testable and unambiguous" ticks are therefore premature.

## Findings (most severe first)

- **[High] No commit identity runs through the run, so "one index per commit" and SC-001 can't be guaranteed.** Sections: FR-004, FR-014, SC-001, Edge Cases "The commit moves", Assumptions "Which commit".
  - Problem: every stage clones the branch tip at its own start, and no stage takes a commit ID (SHA). Evidence:
    - `run(repo, branch, agent_name, version)` (`orchestration/workflows/pipeline_workflow.py:219`);
    - `architect_stage_activity(repo, branch, pr_url, attempt, feedback, seat_id)` (`orchestration/activities.py:389-391`);
    - the architect clones with `--depth 1 --branch` (`harness/architect-agent/agent.py:243`);
    - the sandbox gets `argv = [... repo, branch]` (`orchestration/activities.py:276`) and swe-agent checks out the branch (`harness/swe-agent/agent.py:153-154`).
  - Scenario: the index step resolves branch to SHA X. Someone pushes (the operator, or a plan attempt 2 after a rejection, where attempt 1 already pushed). The candidates' checkout is now Y while every index answer says X. SC-001 still passes, because all candidates share X, yet the index and the checkout disagree.
  - Plan attempts are not covered at all: each attempt after a rejection starts from a commit that the previous attempt pushed.
  - Fix, new FR: "The index step resolves the branch head to one commit and hands that commit and the index outcome to the stage. The stage checks out that exact commit, or, if the branch has moved, records the index as stale (FR-021). Each plan attempt and each Build attempt is a stage start." Rewrite SC-001 to: "candidates' index answers and their checkout name the same commit in 10 of 10 runs".
  - Effort: hours (spec), days (code). Confirmed.

- **[High] "Stale" is never defined, and the Edge Case contradicts FR-010, FR-011 and FR-021.** Sections: FR-011, FR-021, Key Entities "Index use record", Edge Case "The commit moves".
  - Problem: FR-011 and FR-021 say a stage with no ready index starts without the tools. The Edge Case instead uses "the old index ... while the new one builds", which is a build outside any run step and so breaks FR-010. "Old" is also not bounded.
  - Scenario: a Build successor seat (spec 009) starts at a checkpoint commit. Which index it gets, from which branch, and who starts the background build are all undecided. A naive "latest index for this repo" could serve another branch's code.
  - Fix: add to Key Entities: "Stale: the index commit is not the stage's commit but is an ancestor of it on the same branch. Any other index is treated as missing." Rewrite FR-011 and FR-021: "a stage uses the index of its own commit if ready, else the newest ready ancestor index (marked stale), else none." Delete "while the new one builds". All builds happen in a run step (FR-010).
  - Effort: hours. Confirmed.

- **[High] FR-019 (no prompt text) leaves prompts that tell the model the index tools don't exist.**
  - Problem: three prompts say "you have Read/Grep/Glob only": `CANDIDATE_PROMPT` at `harness/architect-agent/agent.py:271`, `GAP_CANDIDATE_PROMPT` at `:298`, and `review_spec`'s prompt at `harness/pm-agent/agent.py:77`. FR-019 forbids changing them, and SC-009 checks the diff for any prompt change.
  - Scenario: candidates follow the instruction and never call `search_code`. The measurement then shows no gain and FR-023 turns the tools off by default. The cause is the prompt, not the tools.
  - Fix: amend FR-019 to "MUST NOT add instructions or content to any prompt. Where a prompt states the agent's tool list (the three lines named above), that statement MUST be corrected to name the index tools, or reworded to drop the 'only'." Amend SC-009 to allow those three lines. The Input's rule ("no prompt text added ... repo_map is a tool only") is about not competing with 019 for the start of the prompt; correcting a false statement doesn't do that.
  - Effort: hours. Confirmed.

- **[High] FR-017's seed source is wrong once Build checkpoints.**
  - Problem: "seeded from the file paths named in the open tasks of the branch's `tasks.md`". The server only sees the indexed commit. But Build runs one session per open task (`harness/swe-agent/agent.py:389-394`, spec 011 F7-a), and its checkpoint commits are not indexed. The harness already knows the current task and the right task file (`_task_files`, `_open_task_ids`, `agent.py:173-210`).
  - Scenario: a successor seat starts after tasks T001 to T004 were ticked in checkpoint commits. The indexed `tasks.md` still shows them open, so `repo_map` seeds from finished work. With several task files, the server can't tell which spec directory is the run's.
  - Fix: "In Build, the harness MUST pass the seed paths of the task the session works on (or of all open tasks for a single-session attempt) to the index tools at session start, through the tool configuration and not the prompt (FR-019). `repo_map` with no paths uses those seeds."
  - Effort: hours. Confirmed.

- **[High] The measurement can't judge the P1 wiring, and its data has no source.** Sections: FR-022, FR-023, SC-007, SC-008, US5, Key Entities "Measurement run".
  - Problem 1: "turns to first correct edit" and "localization hit rate" are defined only for an agent that edits. Architect candidates never edit, so the first wiring (US1) has no metric.
  - Problem 2: both metrics need per-tool-call data (which files were opened or returned before the first edit). Spec 018 FR-004 forbids tool input and output in the ledger. Spec 022 has to add even a turn count to 018 (022's own text). Nothing captures this data today, and the sandbox's session transcripts die with the sandbox.
  - Scenario: US4 slips. The architect has the tools, and the measurement either can't run or rules on Build data for a tool the architect uses.
  - Fix:
    1. Add architect metrics to Key Entities: tokens per candidate, and plan localization (the share of final-diff files that the winning `plan_md` or `tasks_md` names).
    2. Add an FR: "The measurement MUST capture each session's tool calls (tool name, paths touched or returned, turn index) in a measurement log kept in or linked from the spec directory, outside 018's ledger."
    3. State that FR-022's Build arm needs US4.
  - Effort: hours (spec), days (capture). Confirmed for the gap. Conflicts with: 018 FR-004 if anyone tries to put this data in the ledger.

- **[Medium] FR-018 "each agent's tool list" refers to two different settings.**
  - Problem: architect and pm use `tools=[...]` with `permission_mode="default"` (`harness/architect-agent/agent.py:314-321`, `harness/pm-agent/agent.py:294-298`). swe-agent uses `allowed_tools=[...]` with `bypassPermissions` (`harness/swe-agent/agent.py:318-321`). In the installed SDK, `tools` becomes `--tools`, the base built-in set, and `allowed_tools` becomes `--allowedTools`, the auto-approve list (`orchestration/.venv/.../claude_agent_sdk/_internal/transport/subprocess_cli.py:582-598`).
  - Scenario: the index tools are added only to `tools=`. Headless, in default permission mode, an MCP tool call needs approval that nobody can give, so every call is refused and the measurement shows zero use.
  - Fix: in FR-018, "named in `allowed_tools` for every agent, and in `tools` where the agent sets an explicit base set, so that they are offered and pre-approved in that agent's permission mode." Add "is an MCP tool named only in `tools` callable under `permission_mode=default`" to the FR-002 spike.
  - Effort: hours. The flag mapping is confirmed; the refusal is plausible.

- **[Medium] No requirement for in-flight runs or Temporal replay.**
  - Problem: a new index step before the architect stage, and before Build, inserts activity commands into `AgentPipelineWorkflow`. The repo's convention is a `workflow.patched(...)` ID per change (`pipeline_workflow.py:226, 240, 323`). 018 has an explicit FR-028 for this; 021 has none.
  - Scenario: a run waiting on `plan_approved` while the worker restarts on the new code fails replay with a nondeterminism error.
  - Fix, new FR: "Runs started before this feature MUST replay and finish as today, with no index step. New steps and any new stage arguments (commit, index outcome) MUST be guarded, and new activity arguments MUST be optional with today's behaviour as the default."
  - Effort: hours. Confirmed.

- **[Medium] Index build failure modes are missing.** Sections: FR-011, FR-013, Key Entities "Index".
  - Problem 1: if the worker or service crashes mid-build, the index stays "building" and FR-013's lock is never released.
  - Problem 2: the repo's default retry for read-only steps is `_TRANSIENT_RETRY`, 4 attempts (`pipeline_workflow.py:55-60`). A 15-minute build that times out could retry for up to 60 minutes before the run falls back.
  - Problem 3: a cancelled build activity must also kill the indexer processes.
  - Problem 4: readers must never see a half-written index.
  - Scenario: one crash at minute 10 blocks every later run on that commit, or makes them all wait out the full limit.
  - Fix: add to FR-011 and FR-013: "A build past its limit is not retried within the same stage. A 'building' state older than the limit counts as failed and may be taken over. An index becomes 'ready' only when complete; readers never see a partial index. A stopped build stops its indexer processes. The build step holds no subscription seat (it runs outside the seat-lease wrapper, `_with_seat`)."
  - Effort: hours. Plausible.

- **[Medium] The sandbox endpoint is a new trust boundary, and its wording conflicts. Needs human review.** Sections: FR-020, Edge Case "A private target repo", Assumptions "Where it runs".
  - Problem 1: US4 opens the first inbound internet path to the operator's host, and it serves private repo code. The Edge Case says data is "kept only on the factory's own storage", but the Assumption allows "a hosted endpoint", which would move the data elsewhere.
  - Problem 2: FR-020 says the credential is "minted for that run", while Key Entities says "per sandbox". 013 mints per sandbox call (`activities.py:262`), and each seat handoff is a new sandbox.
  - Problem 3: the SDK passes `--mcp-config` JSON as a command-line argument (`subprocess_cli.py:657-682`), so any header credential can be read by the model through Bash, the same class of exposure as `GH_TOKEN`.
  - Scenario: the plan picks a tunnel that also exposes Temporal or LiteLLM, or a hosted index, and nothing in the spec forbids either.
  - Fix:
    1. FR-020: "minted per sandbox invocation, as 013".
    2. Add: "the exposed endpoint serves only the read-only index tools; no other host service is reachable through it."
    3. Settle hosted versus own storage in one sentence.
    4. Accept in writing that the agent can read its own index credential, as with 013's token, and require it in the step's redaction list (`activities.py:263`).
    5. Mark US4 as needing operator security review.
  - Effort: hours. Confirmed for the wording conflicts.

- **[Medium] A target repo can add or shadow MCP servers in swe-agent.**
  - Problem: swe-agent keeps the default `setting_sources`, which loads project settings from the checkout (`harness/swe-agent/agent.py:325-336`). The SDK has `strict_mcp_config` (`subprocess_cli.py` after line 690).
  - Scenario: a branch commits an MCP server config using the index server's name. Its tools then match the `mcp__<server>__*` entries the harness pre-approves, and the agent gets fake answers.
  - Fix: add to FR-018: "swe-agent's MCP servers come only from the harness; a target repo's MCP configuration is ignored." The plan can check that this doesn't break `/speckit-implement` skill discovery.
  - Effort: hours. Plausible.

- **[Medium] FR-012 rules out today's clone credential but doesn't name the one to use.**

  - Fix: "The build MUST use a GitHub App token minted for the target repo with `contents: read` and `metadata: read` (reuse 013's mint client and its grant check, `activities.py:189-219`). The token MUST NOT be stored in the clone's `.git/config` (as `_clone_spec_branch` already ensures, `architect-agent/agent.py:228-246`), in index data, or in service logs."
  - Effort: hours. Confirmed.

- **[Medium] FR-018 doesn't cover the registry entries.**

The architect file has a section "Three roles, three distinct tool bindings" (`registry/agents/architect-agent/SKILL.md:25-40`); the pm file names `tools=["Read","Grep","Glob"]` (`registry/agents/pm-agent/SKILL.md:86-94`).

- **[Medium] FR-021 and SC-002 rely on a record that doesn't exist until 018 ships.**

  - Scenario: the index service is down for a week. Every run quietly falls back to today's tools and nobody notices.
  - Fix: name the interim record, for example "the stage step's result and one worker log line per stage". Add: "the worker logs a warning at start when the index service can't be reached", the same pattern as 011's seat-expiry warning.
  - Effort: hours. Confirmed for the gap.

- **[Medium] The measurement's decision rule is weaker than it looks.** Sections: FR-022, FR-023, SC-008.
  - Problem 1: the tools are added one after another, so each tool's effect depends on the order.
  - Problem 2: 5 to 10 single runs; the report itself says "treat the result as a direction".
  - Problem 3: "lowers the gate pass rate" means one flaky run kills a tool, and today's gate is a binary coverage check that barely depends on code quality.
  - Problem 4: SC-008 passes even when nothing is gained ("still ships"), so it is not a criterion.

  - Fix:

    3. State the number of repeats per task (at least 2) or label the result directional.
    4. Define "lowers the pass rate" as more than one run worse than the baseline.
  - Effort: hours. Confirmed.

- **[Low] SC-003's 2-minute incremental target has no requirement behind it and is likely infeasible for symbols.**

## Tech debt

- **Paid down:** the clone-and-grep work done up to four times per run, and SDK version drift across five lock files (FR-003).
- **Blocking:** today's binary coverage gate makes "gate pass rate" a weak guard (spec 015 would fix this). There is no per-tool-call trace source (see the measurement finding).
