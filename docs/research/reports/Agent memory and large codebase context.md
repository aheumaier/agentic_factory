# Agents learn across runs only through reviewed files in the repo, and a large codebase is a search problem before it is a context problem

*Research report, written 2026-10-17. Sources were accessed 2026-10-17. It is based on the 6 research notes in `docs/research/research_notes/Agent memory and large codebase context/`. Repo citations are `path:line` as of commit `704ed29` and come from note 06 unless marked otherwise. A source marked (secondary) was read through a third party or a search snippet. A source marked (UNVERIFIED) could not be confirmed on any primary page.*

*Amended 2026-10-17: the code search and index part of this report is superseded by [Codebase knowledge index and search for agents](Codebase%20knowledge%20index%20and%20search%20for%20agents.md). That report changes the order of work for search, and it replaces gap rows 7, 8 and 11 below. The gap table now also names the specs that cover each row.*

This report answers two questions about this repo. **First: how does the agent keep memories and learn from its mistakes?** Today it does not, beyond one run: a failed Eval-Gate sends one line of text into the next Build attempt, and nothing survives to the next run. The evidence says the fix is not a memory database. It is **accumulated, structured gate feedback inside a run, plus learned rules written as reviewed lines in the target repo's `AGENTS.md` or `CLAUDE.md`**, each with a citation and an expiry date. **Second: how do we handle a 4-million-line codebase?** Long contexts lose accuracy well before the window is full, so the goal is to keep each session's context small. The order of work is: **keep exploration in subagents, measure tokens per run, and give the agents a shared code index (exact search, symbols and a task-seeded map) outside the sandbox.** The index part, and why it comes earlier than this report first said, is in the [code index report](Codebase%20knowledge%20index%20and%20search%20for%20agents.md). One finding shapes every recommendation. All three agents call the model through the Claude Agent SDK's `query()`, which runs the Claude Code CLI. So the Messages API features (server-side compaction, context editing, the memory tool) do not apply to any path in this repo today. The levers that do apply are the SDK options, the CLI's own settings, and the files in the repo.

## Today the pipeline learns only inside one run

### What carries from one Build attempt to the next

A failed Eval-Gate sets `feedback = f"Eval-Gate failed (attempt {attempt}): {eval_result['reason']}"` (`orchestration/workflows/pipeline_workflow.py:355`), and swe-agent appends it to its prompt (`harness/swe-agent/agent.py:354`). The variable is replaced on every attempt, so attempt 3 sees only attempt 2's failure, not attempt 1's. The reason is one short string: no `spec.md` found, a non-zero sandbox exit code, no PR URL, or "coverage passed" (`eval/braintrust/eval.config.py`). It carries no failing test names, no diff and no per-criterion result. The budget is `MAX_BUILD_ATTEMPTS=3` (`orchestration/workflows/pipeline_workflow.py:40`). The plan loop has its own channel, the `plan_rejected(feedback)` signal (`orchestration/workflows/pipeline_workflow.py:97-99`), which carries a human's words.

### What carries from one run to the next

Nothing that the pipeline writes on purpose. `docs/70-multi-agent-pipeline-design.md` §6.1 gives every activity "its own fresh, memoryless Claude Agent SDK context". Only git commits, PR comments and Braintrust spans cross a stage boundary. All three agents log to Braintrust (`harness/swe-agent/agent.py:35-36`, `harness/pm-agent/agent.py:29-30`, `harness/architect-agent/agent.py:48-49`), but no code reads those traces back. Langfuse runs in docker-compose, but no Python code sends traces to it.

There is one channel that may already work without anyone building it. swe-agent leaves `setting_sources` at its default (`harness/swe-agent/agent.py:325-336`). The Agent SDK docs say that omitting it equals `["user", "project", "local"]`, and that `"project"` loads the repo's `CLAUDE.md` into context ([Agent SDK, Claude Code features](https://code.claude.com/docs/en/agent-sdk/claude-code-features)). So a `CLAUDE.md` in the target repo very likely reaches swe-agent today. This has not been checked in a live run. The architect candidates (`harness/architect-agent/agent.py:313-355`) and pm-agent's `review_spec()` (`harness/pm-agent/agent.py:294-305`) set `setting_sources=[]`, so they would not see it.

## What makes an agent learn from its mistakes

### Feedback from a real check works, self-reflection without one does not

Reflexion raised HumanEval pass@1 from 80.1% to 91% by feeding test results back into the next attempt ([arXiv 2303.11366](https://arxiv.org/abs/2303.11366)). The gain depends on the tests: models asked to correct themselves without outside feedback do not get better, and sometimes get worse ([arXiv 2310.01798](https://arxiv.org/abs/2310.01798)). Production systems keep the loop short. Spotify's background agent has an LLM judge that vetoes about 25% of changes, and the agent fixes about half of those on retry ([Spotify, part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). Stripe's Minions get at most two CI rounds before a human takes over, at 1,300+ PRs per week ([Stripe](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)).

For this repo, that means the Eval-Gate is the oracle, and the quality of what it sends back limits how much the agent can learn. One reason string from three possible outcomes is a weak oracle.

### Memory added selectively helps, memory added wholesale spreads errors

Agents copy past trajectories that look like the current task. When bad records go into memory, the agent repeats and amplifies their errors. A study of this "experience-following" behaviour found that adding only checked records, instead of everything, raised success rates on its test agents. One example is RegAgent, from 55.48% to 70.95% (figures from the paper body, not re-checked on 2026-10-17) ([arXiv 2505.16067](https://arxiv.org/abs/2505.16067)). Other research memory systems report gains of a few points to about 12 points: ReasoningBank +3.4 to 4.6 points on SWE-bench Verified with two Gemini 2.5 models ([arXiv 2509.25140](https://arxiv.org/abs/2509.25140)), Agent Workflow Memory +12 points on WebArena ([arXiv 2409.07429](https://arxiv.org/abs/2409.07429)), and SWE-Exp at 73% on SWE-bench Verified with Claude 4 Sonnet, which note 02 records as an absolute score, not as a gain over the same agent without memory ([arXiv 2507.23361](https://arxiv.org/abs/2507.23361)). ACE (+10.6%) names the failure mode of memory that an LLM keeps rewriting: "context collapse", where repeated rewrites lose detail ([arXiv 2510.04618](https://arxiv.org/abs/2510.04618)).

### In production, memory lives in files, is scoped, is checked when used, and expires

GitHub Copilot's agent memory is the only production system with a published, measured gain. PR merge rate went from 83% to 90% (p < 0.00001). Each memory carries citations to code locations, the citations are checked when the memory is used, and unused memories expire after 28 days ([GitHub](https://github.blog/2026-01-09-building-an-agentic-memory-system-for-github-copilot)). Stripe scopes rule files to directories, so the agent only loads the rules for the code it is in (same Stripe post). OpenAI's harness-engineering write-up keeps `AGENTS.md` to about 100 lines that point into `docs/`, and runs background agents that find drift and open cleanup PRs (secondary, read through a mirror; note 03). A vendor blog argues that agent memory should live in git for the same reasons code does: review, history and rollback ([mintmcp](https://www.mintmcp.com/blog/agent-memory-should-live-git), secondary).

### Memory is an attack surface

MINJA injected malicious records into an agent's memory through normal queries alone, with an attack success rate of 76.8% and an injection success rate above 95% ([arXiv 2503.03704](https://arxiv.org/abs/2503.03704)). OWASP lists memory and context poisoning as ASI06 in its Top 10 for agentic applications (note 03). This pipeline reads untrusted text, such as issue bodies and PR comments. Any memory that an agent writes and a later agent reads without review becomes a way to carry an injection from one run to the next.

### Traces become datasets

Braintrust and Langfuse both describe the same loop: log production traces, pick the failures, turn them into a dataset, and run the eval against that dataset on every change ([Braintrust](https://braintrust.dev/blog/eval-feedback-loops), [Langfuse](https://langfuse.com/docs/evaluation/core-concepts)). This is how a team learns from the agent's mistakes, rather than the agent learning by itself. The repo already writes the traces.

### Anthropic's own memory features, and why most of them don't fit here

Anthropic ships a memory tool (`memory_20250818`, which runs on the client: the model asks for file operations and the application carries them out), context editing (`clear_tool_uses_20250919`) and server-side compaction (`compact-2026-01-12`). The docs for all three were checked on 2026-10-17 ([memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool), [context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing), [compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)). They are Messages API features. Every agent here calls `claude_agent_sdk.query()` (`harness/pm-agent/agent.py:16,154`, `harness/architect-agent/agent.py:22,151-153`, checked by hand on 2026-10-17), which runs the Claude Code CLI. The CLI has its own memory, `CLAUDE.md` files ([Claude Code memory](https://code.claude.com/docs/en/memory)), and its own automatic compaction. The memory tool's file directory would also be a second, unreviewed copy of what `CLAUDE.md` already holds under review. Anthropic's own pattern for long-running agents keeps state in a progress file, a feature list and git, not in hidden state ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). That matches the repo's per-task checkpoint commits (specs/011).

## A 4-million-line codebase: search first, context second

This section explains context rot and why sessions must stay small. For how the agents should search a large repo, read the [code index report](Codebase%20knowledge%20index%20and%20search%20for%20agents.md) instead of the "Search tools at scale" list below. It found a study this pass missed: a structural index raised localization on changes that touch 3 or more files from 44.9% to 91.3% (arXiv 2606.22417).

### Accuracy drops long before the window is full

The research agrees on the direction, though not on the numbers. On NoLiMa, where the question and the answer share no keywords, GPT-4o drops from 99.3% to 69.7% at 32K tokens ([arXiv 2502.05167](https://arxiv.org/abs/2502.05167)). RULER puts the effective context of most models at about half of what they claim ([arXiv 2404.06654](https://arxiv.org/abs/2404.06654)). Models use information at the start and end of a context better than in the middle ([arXiv 2307.03172](https://arxiv.org/abs/2307.03172)). Chroma's tests show accuracy falling as input grows, even on simple tasks ([Chroma](https://www.trychroma.com/research/context-rot)). Spreading one task over many turns cut performance by 39% on average ([arXiv 2505.06120](https://arxiv.org/abs/2505.06120)).

For a large repo, the risk is not that the window is too small. It is that grep output, file reads and old tool results fill the window and push out the spec.

### Most of the context is tool output

In JetBrains' SWE-bench study, hiding old tool output ("observation masking") matched or beat LLM summarization and halved the cost compared with keeping everything ([arXiv 2508.21433](https://arxiv.org/abs/2508.21433)). The paper body puts tool output at about 84% of the context (not re-checked on 2026-10-17). Manus reports keeping errors in context, so the model does not repeat them, and repeating a to-do list at the end of the context to keep the goal in view (secondary, via [tianpan.co](https://tianpan.co/blog/2026/03/02/context-engineering-lessons-from-manus)).

### Search tools at scale

- **Exact search is the baseline, and Anthropic's own agents use it.** Claude Code uses Grep, Glob and Bash rather than a vector index, and Anthropic calls this agentic search "a form of context engineering" ([Anthropic](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)). The discovery pass found no primary Anthropic source that explains why it chose this over embeddings (note 01).
- **A repo map gives the agent a cheap overview.** Aider ranks symbols with PageRank over a tree-sitter graph and fits the map into about 1K tokens (secondary; note 04). An LSP server behind MCP, such as Serena, adds go-to-definition and find-references (secondary; note 04).
- **Indexes pay off at scale, but no benchmark proves how much.** Snap runs Zoekt for code search and says almost all its traffic now comes from agents ([Snap](https://eng.snap.com/code_search)). Cursor reports +12.5% answer accuracy from semantic search on average, and more on large repos, without publishing the method (secondary, [via plushcap](https://www.plushcap.com/content/cursor/blog/cursor-improving-agent-with-semantic-search)). Codebase-Memory indexes the Linux kernel in about 3 minutes ([arXiv 2603.27277](https://arxiv.org/abs/2603.27277)). Windsurf's own docs say its Fast Context degrades above 100K files ([Windsurf](https://docs.windsurf.com/context-awareness/fast-context)). No benchmark found changes only the search tool and keeps everything else fixed (note 04).
- **Large real repos remain hard.** On SWE-bench Pro, the best models solved 23.1% of the public set and 17.8% of the commercial set ([arXiv 2509.16941](https://arxiv.org/abs/2509.16941)).

### Subagents isolate context, and they cost tokens

Anthropic's research system runs subagents that explore in their own context and return only a summary. Multi-agent runs use about 15 times the tokens of a chat, and token use explained 80% of the variance in performance in their browsing evals ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Cognition argues against parallel agents that write code, because they make conflicting decisions ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). The two positions agree on one thing: use subagents for read-only exploration, and keep one agent writing.

## Gap analysis: fresh context is right, and the gaps are in what the gate sends back and what the sandbox clones

### What already matches the evidence

- **Fresh context per activity** (docs/70 §6.1) matches the multi-turn and long-context results. A clean hand-off through git and PR comments is what Anthropic's long-running-agent guidance recommends.
- **One model session per open task, with checkpoint commits** (specs/011 F7-a, `harness/swe-agent/agent.py`) already caps how much one session's context can grow. This is the strongest context-rot defence the repo has.
- **A real oracle exists.** The Eval-Gate is a deterministic check, not self-reflection, so the retry loop has the shape Reflexion needs.
- **Human review gates every durable change** (PR merges, `plan_approved`), so a memory-as-PR design adds no new trust boundary.
- **Traces are already written** to Braintrust from all three agents.

## Conclusion

The evidence points to one design rule. **The agent should not remember anything that a human has not merged.** Learning that pays off in production comes from a precise oracle and from short, cited, expiring rules in the repo. It does not come from an agent that rewrites its own memory. In this pipeline, the cheapest gain is a better oracle: send every attempt's structured failure back, not one replaced string (row 1). The durable gain is a PR that proposes a line for the target repo's `AGENTS.md` after a failure repeats (rows 2 to 4). Before either, one live run should prove that the target repo's `CLAUDE.md` actually reaches swe-agent (row 6).

For a 4-million-line repo, **keep each session small rather than its window large**. The per-task sessions already do most of this. The next steps are an exploration subagent (row 10) and token numbers per run (row 9). For search, follow the [code index report](Codebase%20knowledge%20index%20and%20search%20for%20agents.md): one index per target-repo commit, outside the sandbox, which also makes narrower clones safe (it replaces rows 7, 8 and 11). The Messages API features for memory and compaction are not available on these paths unless an agent moves off the Agent SDK, and nothing found here justifies that move.
