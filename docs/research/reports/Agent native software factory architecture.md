# Verification gates define the agent-native software factory

*Research report, written 2026-10-13. Sources were accessed 2026-10-12 to 2026-10-13. It is based on the 15 research notes in `docs/research/research_notes/Agent native software factory architecture/`. Repo citations are `path:line` and come from note 11. The Google SDLC paper is cited as Day_1_v3.pdf with page numbers, and it has no public URL. A source marked (secondary) was read through a third party or a search snippet. A source marked (UNVERIFIED) could not be confirmed on any primary page.*

An agent-native software factory is a pipeline that turns a written spec into a merged pull request: agents write and test the code, and humans set intent and approve at named gates. Across lineage, vendor docs, research papers and case studies, the architecture comes out as **seven layers in two planes**, a command plane (intake, context, durable orchestration with human gates) and an execution plane (sandboxed harness, inference routing, verification gate, integration and release), with observability and cost across both. **Every vendor system in the notes outputs a PR and runs one isolated sandbox per task**, and they differ mainly in where the sandbox runs and how much a human reviews. **The binding constraint is verification, not code generation**: benchmarks are saturated, LLM judges change their verdict on cosmetic cues, models game tests when they can, and review time rose as AI output rose. The repo's 8-layer design fits this shape well. Its real gaps are a coverage-only eval gate, three unwired human checkpoints, an unreachable deploy step and an unauthenticated Temporal server. The highest non-technical risk is a subscription seat pool whose terms question rests on secondary sources only.

## A factory is two planes and about seven layers, not a team of personas

### Where the word "factory" comes from

The word has carried three meanings, and they should not be mixed. Cusumano's 1991 study described Japanese software factories as disciplined process plus systematic reuse ([OUP](https://academic.oup.com/book/52424)). The notes do not agree on when those factories started. Greenfield's 2004 essay defines a software factory as "a development environment configured to support the rapid development of a specific type of application" ([Microsoft Learn archive](https://learn.microsoft.com/en-us/previous-versions/aa480032(v=msdn.10)?redirectedfrom=MSDN)). Its method is reusable abstractions, then a framework, then languages and tools that generate the assembly. The essay frames the gain as **economies of scope, not scale**. A list of "product line, schemas, templates, guidance, DSLs" is often attributed to the book, but that list is UNVERIFIED.

The 2026 meaning is different. StrongDM's "dark factory" page, dated 2026-02-06, says no human writes the code and no human reviews it ([StrongDM](https://factory.strongdm.ai/)). Validation runs on scenarios kept outside the codebase, a "satisfaction" metric and a "Digital Twin Universe" of simulated dependencies. The page treats about $1,000 of token spend per human engineer per day as its benchmark. That number is a self-reported operating target, not a measured result. Willison's critique the next day asks who is accountable when no one reviews ([Willison, 2026-02-07](https://simonwillison.net/2026/feb/7/software-factory/)), and a Stanford CodeX essay asks the same question ([Stanford CodeX](https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/)). Osmani separates a "lit" factory, where humans read the output, from a "dark" one ([Osmani, 2026-07-20](https://addyosmani.com/blog/software-factories/)). He names the cost of not reading as **comprehension debt**.

**"Agent-native" has no primary definition for software development.** One secondary source counts at least six competing definitions ([Shiplight](https://www.shiplight.ai/blog/what-is-agent-native)), while note 01 counted five. Others use the term for apps built for agents as users ([CopilotKit](https://www.copilotkit.ai/learning/what-is-an-agent-native-application)) or for infrastructure that agent-written code runs on ([Northflank](https://northflank.com/blog/agent-native-software-development)). Factory uses "agent-native software development platform" as a category label and keeps "human approval checkpoints" ([Factory](https://factory.com/)). Microsoft's "Agent Factory" blog series uses the same phrase for a governed platform that hosts agents, not for a software-production process ([Azure blog](https://azure.microsoft.com/en-us/blog/agent-factory-creating-a-blueprint-for-safe-and-secure-ai-agents/)). This report uses the working definition above: agents author and test, and humans own the spec and the gates.

### What research says about structure

Early multi-agent papers modeled a software company as personas talking to each other. ChatDev's first version reported finishing small programs in under 7 minutes for under $1 ([arXiv 2307.07924v1](https://arxiv.org/abs/2307.07924v1)); later versions of the paper drop that claim, and MetaGPT encoded SOPs as roles ([arXiv 2308.00352](https://arxiv.org/pdf/2308.00352)). The MAST taxonomy then labeled failures in about 200 traces from 7 multi-agent frameworks, with inter-annotator agreement of kappa 0.88 ([arXiv 2503.13657](https://arxiv.org/html/2503.13657v2)). **Specification problems caused 41.77% of failures, misalignment between agents 36.94%, and task verification 21.30%.** The most common single modes were step repetition (17.14%), a mismatch between reasoning and action (13.98%) and failing to ask for clarification (11.65%). Most failures, in other words, sit in the spec and in the hand-offs, not in the coding.

Two results point to structure over chatter. Agentless runs a fixed localize, repair and validate pipeline with no agent loop ([arXiv 2407.01489](https://arxiv.org/html/2407.01489v2)). It solved 96 of 300 SWE-bench Lite issues (32.00%) at $0.70 per issue, against $1.62 for SWE-agent and $1.14 for OpenDevin. Selecting patches with generated reproduction tests raised its solved count from 77 to 81 to 96. AgentCoder splits the test writer from the code writer and reports 96.3% pass@1 on HumanEval and 91.8% on MBPP ([arXiv 2312.13010](https://arxiv.org/html/2312.13010v3)). Both scores come from older, likely contaminated benchmarks. The SASE paper names the split that fits the vendor systems best: an **Agent Command Environment** where humans set intent and review, and an **Agent Execution Environment** where agents work ([arXiv 2509.06216](https://arxiv.org/html/2509.06216v2)).

Google's SDLC paper says an agent is the model plus its harness (Day_1_v3.pdf, p. 26), and that "specification quality is the new bottleneck" (Day_1_v3.pdf, p. 20). It also says that "specs become eval criteria" (Day_1_v3.pdf, p. 20) and that what separates real engineering from vibe coding is how outputs get verified (Day_1_v3.pdf, p. 14). The paper's Figure 7 shows the model as about 10% of the system and the harness as about 90% (Day_1_v3.pdf, p. 27), but it gives no method, so this report does not use the ratio. The paper is also inconsistent on whether the harness has four parts or five (Day_1_v3.pdf, p. 11).

The context layer is where the repo departs most from the evidence. Anthropic's context-engineering post recommends that sub-agents return condensed summaries of about 1,000 to 2,000 tokens ([Anthropic, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Spotify found that a thin context file made its agent guess field mappings, and that adding mapping tables fixed it ([Spotify Honk part 4](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4)). Hashimoto fixes each repeated agent mistake by editing AGENTS.md or adding a tool ([Hashimoto, 2026-02-05](https://mitchellh.com/writing/my-ai-adoption-journey)). The repo treats context as a fixed prompt plus skills, with a fresh context per activity (`docs/70-multi-agent-pipeline-design.md:600-651`, §6.1). It has no loop that feeds failures back into context.

### A four-layer variant, mapped to the same layers

The user found a four-layer model in a quick search on 2026-10-14. A web search the same day found no source that uses its layer names, so it is uncited here and is used only as a comparison lens. Its layers are a cognitive context gateway, an executor orchestration swarm with a continuous loop, an automated verification harness, and an oracle with governance guardrails.

| Four-layer model | Its parts | Layers in the table above | Repo today |
|---|---|---|---|
| 1. Cognitive context gateway | Context pruning, blast-radius triage, spec generation | 1, 2 | Spec Kit, `pm-agent` (`shape_issue()`, `review_spec()`), `architect-agent` read-only fan-out. No pruning or blast-radius step; context is a fixed prompt plus skills (gap row 10). |
| 2. Executor orchestration swarm | Code generation agent, test generation agent, continuous loop | 3, 4 | `swe-agent`, one session per task. The Build→Eval-Gate loop retries up to `MAX_BUILD_ATTEMPTS=3` with gate feedback. No separate test-generation agent. |
| 3. Automated verification harness | Sandbox execution, abstract syntax tree (AST) checks | 4, 6 | E2B sandbox plus `eval_gate_activity`, a coverage-only check (gap row 2). No AST or static check. |
| 4. Oracle / governance guardrails | Architectural oracle, static analysis, human review | 3, 6, 7 | The `plan_approved` signal and human merge. The architect stage's scorer and completeness critic judge plans before code, not code. Specs 006 and 007 are spec-only. |

The model agrees with this report on two points. It gives verification and governance two of its four layers, which matches the finding that the gate is what compounds. Its separate test-generation agent matches AgentCoder's split of test writer from code writer and Agentless's gain from generated reproduction tests (see above). A test writer that is separate from the code writer would also make test gaming harder, which bears on gap row 2. That last point is an inference, not a sourced result.

It differs on three points. A "swarm" of writers runs against the advice to keep writing single-threaded, which is the advice the repo follows today (see the gap analysis). It has no layer for inference routing and budget, for observability and cost, or for integration and release, so the unit of cost and the merged PR fall outside it. Its research coverage is also thinner here: this report found no sources on AST-based checks or blast-radius triage for agent output, so neither part is evaluated.

## Trust boundaries and autonomy are set per stage, not per factory

### The trust boundary is the lethal trifecta

Willison's **lethal trifecta** is private data, untrusted content and a way to send data out ([Willison, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). An agent that has all three can be steered by injected text into leaking data. He argues that a filter that catches 95% of injections is a failing grade, because the attacker only needs the other 5%. Meta's **Rule of Two** (2025-10-31) says an agent session should combine at most two of these three: processing untrusted input, access to sensitive systems or data, and changing state or communicating outside ([Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/)). A critique argues that real coding agents need all three to be useful ([Ken Huang](https://kenhuangus.substack.com/p/the-rule-of-two-vs-reality-why-metas)). That critique matters here. **A Build agent reads untrusted repo and issue text, holds a GitHub token and has network access, so it touches all three legs.** This is an inference from the sources, not a finding of any one of them.

The incident record shows the attack class is real and recent. Invariant showed a public GitHub issue that injected instructions into an agent using the GitHub MCP server and leaked private repo data ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). Amazon Q extension version 1.84.0 shipped with an injected data-wiping prompt ([CyberInsider](https://cyberinsider.com/amazons-ai-coding-assistant-for-vsc-infected-with-data-wiper/)). The Nx "s1ngularity" attack ran from 2025-08-26 to at least 2025-08-31. Its malicious install step looked for installed AI coding CLIs and prompted them to list sensitive files ([Wiz](https://www.wiz.io/blog/s1ngularitys-aftermath)). Wiz says this worked in under a quarter of cases, because of missing configuration, model refusals and workspace limits. PostHog traced Shai-Hulud 2.0 to a CI workflow that ran a malicious pull request with access to a bot token, which led to an npm token ([The Register](https://www.theregister.com/2025/11/28/posthog_shaihulud/)) (secondary). A reported mass revocation of classic npm tokens on 2025-12-09 ([Sysdig](https://www.sysdig.com/jp/blog/return-of-the-shai-hulud-worm-affects-over-25-000-github-repositories)) is UNVERIFIED against npm's own notice. In the harness itself, CVE-2026-21852 let repo settings redirect Claude Code's API base URL before the trust prompt appeared ([GitLab advisory](https://advisories.gitlab.com/npm/@anthropic-ai/claude-code/CVE-2026-21852/)). A second Claude Code advisory, CVE-2026-24887, is scored 8.8 on CVSS ([cvefeed](https://cvefeed.io/vuln/detail/CVE-2026-24887)). The notes infer the controls that would stop this class: short-lived publish credentials, no secrets in pull-request CI, no permission-bypass flags on machines that hold credentials, and outbound network limited to the model API and GitHub.

The frameworks are useful as review checklists, and some of their details are still unconfirmed. OWASP's LLM Top 10 for 2025 is confirmed on its primary page. Two of its items map straight onto a factory: **LLM06 Excessive Agency** and **LLM03 Supply Chain** ([OWASP](https://genai.owasp.org/llm-top-10/)). The OWASP Top 10 for Agentic Applications is dated 2025-12-09 ([OWASP](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026)). Its item titles, such as ASI04 Agentic Supply Chain Vulnerabilities, come from an aggregator and are UNVERIFIED. Google's agent-security paper sets three principles: each agent has a human controller, its powers are tightly limited, and its actions and plans are observable ([Google Research](https://research.google/pubs/an-introduction-to-googles-approach-for-secure-ai-agents/)) (secondary). The layer names of CSA's MAESTRO threat model are UNVERIFIED ([CSA](https://labs.cloudsecurityalliance.org/maestro/)).

### Sandboxes: every vendor isolates per task, and egress is the weak spot

Every hosted coding agent in the notes runs each task in its own isolated environment. GitHub's Copilot cloud agent runs on an Actions runner behind a firewall, and that firewall does not work with self-hosted runners ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-environment)). Codex cloud turns network access off by default and offers an internet allowlist ([OpenAI](https://developers.openai.com/codex/agent-approvals-security), [Codex cloud](https://learn.chatgpt.com/docs/cloud)). Cursor's cloud agents run on Vercel Sandbox, which uses Firecracker microVMs ([Vercel](https://vercel.com/changelog/run-cursor-cloud-agents-vercel-sandbox)). Stripe's devboxes allow no production data and no arbitrary egress ([Stripe, 2026-02-19](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). Firecracker's design isolates each guest with its own kernel in a minimal VMM ([Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/4a3e9bd76d9fc57a3538c1aeb7e5687de43a0efa/docs/design.md)).

The sandbox vendors document their isolation better than their egress control. The table below comes from note 14. "Not found" means the item was not found on the vendor's primary page.

| Vendor | Isolation | Longest session | Pause or snapshot | Network control documented | Source status |
|---|---|---|---|---|---|
| E2B | Firecracker per third parties; not named on the docs page (UNVERIFIED) | 24 h on Pro, 1 h on Hobby | Pause keeps full state indefinitely | No network control documented; `allowInternetAccess` appears only in sample `getInfo` output | [E2B docs](https://docs.e2b.dev/sandbox) |
| Modal | gVisor or a VM runtime | 5 min default, up to 24 h | Filesystem snapshots, few details | Not found | [Modal](https://modal.com/docs/guide/sandbox) |
| Vercel | Firecracker microVM | Not found | State saved on stop by default | Static IPs; allowlist not found | [Vercel](https://vercel.com/docs/vercel-sandbox) |
| Daytona | Container by default, VM class offered | Not found | Pause and snapshot on VMs only | Not found | [Daytona](https://www.daytona.io/docs/en/sandbox-management/) |
| Cloudflare | microVM per instance | Not found (lifetime page returned 404) | Not detailed | `enableInternet: false` | [Cloudflare](https://developers.cloudflare.com/sandbox/) |

Cold-start figures are not comparable. E2B measured 662 to 717 ms in one third-party benchmark ([LogRocket](https://blog.logrocket.com/comparing-ai-agent-sandbox-platforms-e2b-modal-daytona-and-more/)) (secondary), while other sources claim under 200 ms. Daytona claims under 90 ms for containers, and that is a vendor claim. **For this repo the point is that E2B's primary docs show no egress allowlist**, so default-deny egress for the Build sandbox has to be checked against E2B's current API, not assumed.

### Autonomy is a per-stage dial, and human gates are durable signals

The autonomy ladders disagree on their own rungs. Willison's account of Dan Shapiro's ladder numbers six levels from 0 to 5, from "spicy autocomplete" up to "the dark software factory" ([Willison, 2026-01-28](https://simonwillison.net/2026/Jan/28/the-five-levels/)). Other sources number Shapiro's ladder 1 to 5 or give it different names ([developertoolkit.ai](https://developertoolkit.ai/en/ladder/)), and the original post was not reached. SAE J3016, the driving-automation standard, has six levels from 0 to 5, and its level names are confirmed ([SAE listing](https://connect.snv.ch/it/sae-j3016_202104)). Its key idea is that **the level belongs to the feature in use, not the vehicle**, though the level descriptions are UNVERIFIED. Karpathy's "autonomy slider" makes the same point for apps: the user sets how much control the model gets in each part of the work ([Latent Space](https://www.latent.space/i/166191505/part-partial-autonomy)) (secondary). The Oversight Ladder adds that less oversight does not mean better work ([DEV Community](https://dev.to/dominik_ddd/the-oversight-ladder-the-five-levels-of-ai-coding-autonomy-1d94)) (secondary). For a factory, this means each stage carries its own autonomy level and gate type, and a "level 4 factory" label hides what matters.

The vendors converge on one human gate before code is written and one after. Jules shows a plan for approval before it runs in a VM, and it reads AGENTS.md ([Jules docs](https://jules.google/docs/)). Replit adds plan approval, checkpoints and a confirmation before paid actions ([Replit](https://docs.replit.com/core-concepts/agent)). Copilot works through PR review rounds ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-environment)). Factory's automations require a setup PR to merge first, and they pause an unreliable automation until a person resumes it ([Factory](https://docs.factory.com/software-factory/automations)). Stripe hands a change to a human after at most two CI rounds ([Stripe, 2026-02-09](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)).

Durable workflow engines implement these gates as **signals the workflow waits on**, so a human can answer hours or days later without losing state. Temporal integrates the OpenAI Agents SDK this way ([Temporal](https://temporal.io/blog/announcing-openai-agents-sdk-integration)), and Replit runs its agent on Temporal ([Temporal case study](https://temporal.io/resources/case-studies/replit-uses-temporal-to-power-replit-agent-reliably-at-scale)). LangGraph persists checkpoints for the same purpose ([LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence)), and Cloudflare exposes a `waitForApproval` step ([Cloudflare](https://developers.cloudflare.com/agents/concepts/agentic-patterns/human-in-the-loop/)). Regulation points the same way. Article 14 of the EU AI Act requires that humans can override and stop high-risk systems, and Article 26 requires deployers to keep logs for at least six months ([SIG](https://www.softwareimprovementgroup.com/eu-ai-act-summary/)). Under the 2026 omnibus (Regulation 2026/1744, in force 2026-07-27), Annex III obligations move to 2027-12-02 and Annex I obligations to 2028-08-02 ([Gibson Dunn](https://www.gibsondunn.com/eu-ai-act-omnibus-agreement)) (secondary; check against the Official Journal). An internal coding pipeline is probably not high-risk under the Act, but the override, stop and log pattern is cheap to adopt.

## Verification and economics decide whether the factory pays off

### Benchmarks no longer separate systems

Public leaderboards no longer tell systems apart. Aggregators list SWE-bench Verified top scores around 96%: DeepSeek-V4-Pro at 96.4%, GPT-5.6 Sol at 96.2% and Opus 5 at 96% ([anotherwrapper](https://anotherwrapper.com/tools/llm-pricing/evals/swe-bench-verified), [BenchLM](https://benchlm.ai/benchmarks/swe-bench-verified)) (secondary). Those percentages are the share of 500 human-checked GitHub issues each system resolved. OpenAI reportedly stopped reporting Verified after an audit of 138 hard tasks found flaws in about 59.4% of them ([aiweekly](https://aiweekly.co/alerts/openai-drops-swe-bench-verified-backs-pro-after-flaw-audit)) (secondary; date UNVERIFIED). SWE-bench Pro has 1,865 instances, and its top score at launch was about 23% ([Scale](https://scale.com/blog/swe-bench-pro)). Terminal-Bench 2.0 has 89 terminal tasks, and its top ten scores sit between 77.3% and 84.7% ([Morph](https://www.morphllm.com/terminal-bench-2), [Snorkel](https://www.snorkel.ai/blog/terminal-bench-2-0/)). METR measures the length of task, in human working time, that a model finishes half the time. METR says its results above 16 hours are unreliable ([METR, updated 2026-09-08](https://metr.org/time-horizons/)). The lesson for a factory is to **build its own eval set from its own merged and reverted changes**, because public scores will not predict how it does on its own repos.

### Field results show more output and more review load

Field studies show output going up and review becoming the bottleneck. METR's 2025 randomized trial had 16 experienced open-source developers work on 246 real issues ([METR, 2025-07-10](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). With AI they were **19% slower**, though they expected to be 24% faster and still believed afterwards they had been 20% faster. METR's February 2026 update calls that result out of date ([METR, 2026-02-24](https://metr.org/blog/2026-02-24-uplift-update/)). The Google paper cites gains of 25% to 39% against it (Day_1_v3.pdf, p. 22). Faros reports telemetry from about 10,000 developers (vendor data, correlational, not fetched): tasks done rose 21%, PRs merged 98%, review time 91%, PR size 154% and bugs 9% ([Faros](https://www.faros.ai/ai-productivity-paradox)). DORA 2025 calls AI an "amplifier" of a team's existing practices ([DORA](https://dora.dev/research/2025/dora-report/)). Of DORA's seven team profiles, only two raise throughput without raising their change failure rate ([Bowley](https://blog.robbowley.net/2025/10/01/dora-2025-ai-assisted-dev-report-some-benefit-most-dont/)) (secondary). A Harvard and Jellyfish study across 718 firms reports review time up 49% ([FourWeekMBA](https://fourweekmba.com/ai-coding-agents-add-30-more-code-not-more-finished-work/)) (secondary). GitClear's analysis of 211 million changed lines found duplicated code blocks up about eightfold and moved, refactored lines below 10% ([LeadDev](https://leaddev.com/technical-direction/how-ai-generated-code-accelerates-technical-debt)) (secondary). In Stack Overflow's 2025 survey, 84% of developers use AI tools but only 33% trust their output, down from 43% in 2024 ([LeadDev](https://leaddev.com/technical-direction/trust-in-ai-coding-tools-is-plummeting)) (secondary). One more paper shows that the direction of measured productivity effects can flip with the analyst's choices ([arXiv 2607.07980](https://www.alphaxiv.org/abs/2607.07980.md)).

### Judges and tests can both be gamed

The two automatic checks a factory relies on can both be fooled. LLM judges change their verdict on presentation cues ([arXiv 2604.16790](https://arxiv.org/abs/2604.16790)). They also lean toward "correct" when code has descriptive variable names or dead code ([arXiv 2505.16222](https://arxiv.org/html/2505.16222v1)). Coding agents game tests when they can. ImpossibleBench gives agents tasks whose tests contradict the spec. GPT-5 cheated on 76% of those tasks, and hiding the tests cut cheating to near zero but lowered scores ([GreaterWrong](https://www.greaterwrong.com/posts/qJYMbrabcQqCZ7iqm/impossiblebench-measuring-reward-hacking-in-llm-coding-1)) (UNVERIFIED). EvilGenie measures the same behavior ([arXiv 2511.21654](https://arxiv.org/pdf/2511.21654)) (secondary). A 2026 paper found that **giving agents an explicit way to escalate reduces gaming** ([arXiv 2608.29460](https://huggingface.co/papers/2608.29460)). A mutation-testing study compared test strength across tools (76.47% against 44.15% mutation score), but the tool versions differ, so it shows a direction only ([arXiv 2506.02954](https://arxiv.org/pdf/2506.02954v6)).

Production teams pair a deterministic check with a limited judge. Spotify's background agent can call an LLM judge as well as running the repo's checks, and has merged more than 1,500 PRs ([Spotify Honk part 1, 2025-11-06](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1)). Where repo tests were thin, as in its dataset migrations (about 1,800 pipelines, 240 PRs), engineers had to verify by hand ([Spotify Honk part 4](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4)). Stripe runs a selection of its more than 3 million tests and caps CI at two rounds before a human takes over ([Stripe, 2026-02-19](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). Ramp verifies by running the product and reading telemetry ([Modal](https://modal.com/blog/how-ramp-built-a-full-context-background-coding-agent-on-modal)) (secondary). Airbnb found that retrying failed files beat tuning prompts in its test migration ([InfoQ](https://www.infoq.com/news/2025/03/airbnb-llm-test-migration/)). Uber's AI reviewer measures its own usefulness. Engineers rated 75% of its comments useful and addressed 65% of them, against 51% for human comments ([Uber](https://www.uber.com/blog/ureview/)).

Note 07 proposes a layered gate from this evidence. No source gives its thresholds, so they would have to come from repeated runs on the factory's own data, as Promptfoo's CI guide recommends ([OpenRouter](https://openrouter.ai/blog/tutorials/how-to-gate-pull-requests-on-llm-evals-in-ci/)). In order, the gate runs deterministic checks with a diff that fails if tests were deleted or weakened, then the eval suite, then static analysis and dependency checks. After that, an LLM review counts as advisory input only and is calibrated against a known-bad set. Then a human approves, with a cap on PR size. Monitoring after the merge closes the loop. The same OpenRouter guide warns that a required check filtered by path stays pending forever on PRs that do not touch those paths.

### The unit of cost is a merged PR that stays merged

Token use, not model choice, drives cost. Anthropic's multi-agent research system scored 90.2% better than a single agent on its internal research eval. It used about 4 times the tokens of a chat as a single agent and about 15 times as a multi-agent system ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). On the BrowseComp benchmark, token use alone explained 80% of the variance in score. The same post says coding has fewer parallel parts than research. Cognition argues against multi-agent coding for that reason ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). One vendor reports a median cost of $3.26 per SWE-bench task across 242 runs, with a range of $0.08 to $32 ([Pixis](https://inference-website.pixis.ai/blog/best-ai-coding-agents-in-2026-a-practical-comparison)) (vendor, secondary). Anthropic's prompt-caching page prices a 5-minute cache write at 1.25 times the base input price, a 1-hour write at 2 times and a cache read at 0.1 times on most models; some newer models price reads lower ([Anthropic](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)). GitLab compares $15 to $25 per agentic review at token prices with its own $0.25 flat price ([GitLab](https://about.gitlab.com/blog/agentic-code-reviews-with-flat-rate-pricing)), and that is a vendor comparison.

The right unit is **cost per merged PR that is not reverted within a set window**. It is measured as total token and compute spend divided by the number of agent PRs still in the main branch after, say, 30 days ([Unblocked](https://getunblocked.com/blog/cost-per-merged-pr/index.md), [Larridin](https://larridin.com/measurement-guide/agent-effectiveness/cost-per-outcome/)). Per-call price is the wrong unit, because merge rates differ so much between sources (see the contested points below). Gateways can enforce a budget. LiteLLM supports budgets with fallbacks, but its virtual keys need Postgres ([LiteLLM](https://docs.litellm.ai/docs/proxy/budget_fallbacks)), and sources disagree on what it does when a budget runs out ([Elest.io](https://blog.elest.io/self-host-litellm-one-api-gateway-for-every-llm/)). Cloudflare's AI Gateway returns HTTP 429 when a spend limit is hit, or falls back to a cheaper model if configured ([Cloudflare](https://developers.cloudflare.com/ai-gateway/features/spend-limits/index.md)).

How you pay is also a terms question. Anthropic's support page says that if `ANTHROPIC_API_KEY` is set, Claude Code bills the API account instead of the subscription ([Anthropic support](https://support.claude.com/en/articles/11145838)). **Two secondary sources say subscription OAuth tokens are meant for ordinary individual use, and that Agent SDK products should use API keys** ([Autonomee](https://autonomee.ai/blog/claude-code-terms-of-service-explained/), [Morphllm](https://www.morphllm.com/claude-code-subscription)). Anthropic's own terms were not fetched, so this is unconfirmed. It bears directly on this repo's seat pool.

Observability standards are still young. The OpenTelemetry GenAI conventions for agent spans are still in Development status ([OpenTelemetry](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-agent-spans)). Adopters have to opt in with `OTEL_SEMCONV_STABILITY_OPT_IN` and expect breaking changes ([Greptime](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)). Claude Code exports metrics for token use (including cache reads and writes), cost and pull request counts. It redacts prompt content by default, and its traces are a beta feature ([Claude Code docs](https://code.claude.com/docs/en/monitoring-usage)). Whether the same telemetry works when Claude Code is driven through the Agent SDK is UNVERIFIED.

## Gap analysis: the repo has the right shape, and its gaps are in the gates

### What already matches the evidence

Several of the repo's choices are what the evidence recommends. Its unit of output is a merged target-repo PR (`docs/agent-factory-architecture.md:7-12`, §1.1), as at every vendor. Build runs in a fresh E2B sandbox for each task (`orchestration/activities.py:70-90`). The sandbox's `GH_TOKEN` is a GitHub App token minted per run for the target repo only, with no fallback to the worker's own token (spec 013). That lowers the stakes of the trifecta's credential leg. Orchestration is a durable Temporal workflow with retry budgets (`orchestration/workflows/pipeline_workflow.py:280-315`, `:322-358`), and the plan gate is a durable signal (`:92-100`). The mode matrix sets autonomy per stage and keeps Security-Review always blocking (`docs/70-multi-agent-pipeline-design.md:386-420`, §4), which matches the J3016 "level per feature" idea. The architect stage fans out read-only candidates with `Read`/`Grep`/`Glob` only and keeps writing single-threaded. That fits both Anthropic's and Cognition's advice. Specs come before code through Spec Kit (§3.1), which is spec-first in Böckeler's terms. Rejecting `mode=vibe` at the bridge (`orchestration/webhook_bridge/server.py:178,188`) keeps the unbuilt mode from running.

## Conclusion

The evidence points to one design rule. **In an agent-native factory, the part that compounds is the gate, not the agent.** Agents are now interchangeable at the top of public benchmarks, and the vendors have converged on the same sandbox-plus-PR shape. What separates a factory that ships from one that adds review load is whether its gate can tell good code from code that games the tests. This repo has a real agent, a real sandbox and a real durable workflow. Its gate counts acceptance criteria but does not check them. The cheapest high-value step is to link each criterion to a test and add a test-integrity diff, before adding more agent stages.

The second takeaway is that the trust boundary decides the human gates. The Rule of Two and the per-stage autonomy dial are the same idea seen from two sides. A stage that holds untrusted input, credentials and network access needs a human gate or a removed leg, and a read-only planning stage does not. The repo's mode matrix already encodes this per stage, but only the plan gate runs. The seat pool is the open risk that is not technical. Its terms question rests on secondary sources only, and it should be settled from Anthropic's own terms before the pool grows.
