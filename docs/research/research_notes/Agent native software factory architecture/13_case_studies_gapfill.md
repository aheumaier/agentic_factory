## 1. OpenAI "harness engineering"

### Takeaway
Primary post still not readable (HTTP 403 to WebFetch, 2026-10-13). All figures are secondary and mutually inconsistent. Treat as UNVERIFIED.

### Cited findings
- Team built an internal product of about 1M lines with no hand-written code, starting from an empty repo in late August 2025 with Codex CLI — [Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/openai-software-factory) and [Towards AI](https://pub.towardsai.net/openais-harness-engineering-experiment-zero-manually-written-code-100a24ad04cf) (both secondary; the second is a summary of Ryan Lopopolo's write-up).
- About 1,500 PRs merged in five months, about 3.5 per engineer per day; team grew from 3 to 7 — [secondary summary, search snippet](https://www.zenml.io/llmops-database/extreme-harness-engineering-building-production-software-with-zero-human-written-code). UNVERIFIED against OpenAI.
- Repo holds AGENTS.md as a table of contents pointing to a structured docs/ directory — [36Kr](https://eu.36kr.com/en/p/3715546375188870) (secondary).
- When an agent failed, the team asked what capability, context or structure was missing (same secondary sources).
- Accounts conflict on whether humans review code before merge. Not found: a primary statement.

### Inferences
- The "missing capability" loop matches our Build/Gate design: each failure should add a check, doc or tool.

### Gaps
- Primary text, architecture (the "Symphony" orchestrator name appears only in secondary sources, UNVERIFIED), and any merge policy.

**Implication for factory architecture:** Record each agent failure as a repo artifact (doc, lint rule, tool) so the next run gets it for free. Do not rely on prompt length.

## 2. Stripe "Minions"

### Takeaway
Stripe's own posts describe unattended coding agents that produce over 1,000 merged PRs a week, each human-reviewed. The main levers were pre-built devboxes, a bounded CI retry, and a curated tool set. Part 1 and Part 2 disagree on the tool count.

### Cited findings
- Part 1 (2026-02-09): "Over a thousand pull requests merged each week at Stripe are completely minion-produced"; devboxes "pre-warmed so one can be spun up in 10 seconds" — [Stripe, Minions Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents) [fetched, self].
- Part 1: central MCP server "hosts more than 400 MCP tools." CI: "often one, at most two, CI runs—and only after we've fixed everything we can locally." Human review: PRs "are human-reviewed. They contain no human-written code." [fetched, self].
- Part 2 (2026-02-19): "Over 1,300 Stripe pull requests" merge weekly; "Nearly 500 MCP tools"; devboxes are AWS EC2 instances with a warm pool and cached builds; over three million existing tests give feedback; about half a dozen devboxes per engineer — [Stripe, Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2) [fetched, self].
- Orchestration: "Blueprints," code-defined state machines mixing deterministic and agent nodes. Devboxes have no production data and no arbitrary egress — Part 2 [fetched, self].
- After the second CI round a branch goes back to a human for "manual scrutiny" — Part 2 [fetched, self].

### Inferences
- The 400 vs 500 tool count is a number that changed between posts in four weeks; quote it as "400-500" or cite the post.

### Gaps
- How humans review about 1,300 PRs a week: not stated. Independent verification: not found.

**Implication for factory architecture:** Our Build/Gate loop matches Stripe's shape: deterministic steps around the agent, a two-run CI cap, then a human. Keep the agent's tool list small per task, and keep sandbox data non-production.

## 3. Google: internal code migrations and AI share

### Takeaway
The arXiv paper (2501.06972, submitted 2025-01-12) does have numbers in its full text, which the abstract lacks. They are migration-specific. Google's company-wide share is a 2024 earnings-call figure.

### Cited findings
- Full text (Nikolov et al.): "80% of the code modifications in the landed CLs were fully AI-authored" (int32 to int64 migration, Section IV); "∼87% of the code generated by AI ended up committed without any change" (JUnit3 to JUnit4, Section V); migration time "reduced by an estimated 50%" by engineers' estimate (Section IV); JUnit3 to JUnit4 touched 5,359 files and over 149,000 lines in 3 months (Section V); a 500M+ line codebase — [arXiv HTML v1](https://arxiv.org/html/2501.06972v1) [fetched, self].
- A secondary summary gives "39 migrations," "595 code changes," "93,574 edits," and "74.45% of the code changes" LLM-generated. We did not find these in the fetched text. UNVERIFIED; do not cite until checked in the PDF.
- Company-wide: Sundar Pichai said on the Q3 2024 earnings call (2024-10-29) that "more than a quarter of all new code at Google is generated by AI, then reviewed and accepted by engineers." Source: [Fortune, 2024-10-30](https://www.fortune.com/2024/10/30/googles-code-ai-sundar-pichai) [secondary coverage of a self claim]. No later figure found.
- Paper's own success bar: "at least a 50% acceleration in task completion rate" (Section I) [fetched, self].

### Gaps
- No independent review-rate or defect data. The paper is an experience report, with no comparison arm.

**Implication for factory architecture:** Migration work with a mechanical checker reaches high AI-authored share. Count "AI-authored" and "accepted without change" separately in our metrics; they differ (80% vs 87%).

## 4. Microsoft and Amazon claims

### Takeaway
Both are leadership estimates made in public, not measured program data. Amazon's Java figures are the most specific, and they are self-reported.

### Cited findings
- Microsoft: Satya Nadella at Meta's LlamaCon (2025-04-29): "I'd say maybe 20%, 30% of the code that is inside of our repos today." Source: [TechRepublic](https://www.techrepublic.com/article/news-microsoft-meta-code-written-by-ai/) [secondary of a verbal estimate]. CTO Kevin Scott's "95% by 2030" is a forecast, not a current claim.
- Amazon: Andy Jassy's post (August 2024, as reported): upgrade to Java 17 went from "about 50 developer-days to a few hours"; "We estimate this has saved us the equivalent of 4,500 developer-years"; "an estimated $260M in annualized efficiency gains"; over 50% of production Java systems upgraded in under six months — [The Decoder](https://the-decoder.com/amazons-ai-assistant-saves-4500-years-of-development-time-ceo-andy-jassy-says/) and [AWS DevOps blog](https://aws.amazon.com/blogs/devops/accelerate-application-upgrades-with-amazon-q-developer-agent-for-code-transformation/) for the product context [both secondary; LinkedIn primary not fetched]. Amazon's method, per AWS: estimate from the number of Java dependencies migrated, and cost from hosts removed; Amazon calls the estimates "conservative."
- Incentive caveat: the source sells the product. Some launch problems reported (incorrect outputs from a rushed deployment) — secondary (Benzinga).

### Gaps
- The Jassy primary post, and "developer-years" wording in AWS posts: not found. Verified-by-third-party: none.

**Implication for factory architecture:** A time-saved number is a model of effort, not a measurement. Our reports need the same disclosure: say what was counted and how.

## 5. Uber (uReview, migrations), Shopify, Coinbase

### Takeaway
Uber's uReview post is the only one here with a full, primary evaluation. Coinbase gives a headline share, self-reported. Shopify gives adoption, not code share.

### Cited findings
- Uber uReview (2025-08-12) [fetched, self]: Commenter is a multi-stage pipeline (filter files, generate comments with three assistants for bugs/best practice/AppSec, grade with a second prompt, merge duplicates, suppress weak categories). Developers mark 75% of comments "Useful"; 65% of comments are addressed in the same changeset; human-written comments are addressed 51% of the time (author judgment). Runs in CI with a median of 4 minutes. Estimated 1,500 hours saved a week, "nearly 39 developer years annually" (estimate). Source: [Uber blog](https://www.uber.com/blog/ureview/). Note the post's own inconsistency: "weekly ~65,000 diffs" and "65,000 per month."
- Uber migrations (secondary only, [ZenML](https://zenml.io/llmops-database/llm-driven-developer-experience-and-code-migrations-at-scale), [Zylos](https://zylos.ai/research/2026-04-18-llm-powered-code-migration-at-scale)): Java-to-Kotlin; LLM writes deterministic AST rules instead of direct code, because of hallucination risk. Timeline "eight years to four" is a projection. Primary Uber migration post not found.
- Coinbase (self, via [Cointelegraph](https://cointelegraph.com/news/coinbase-says-ai-writes-nearly-half-of-its-code)): Head of Platform Rob Witoff: 95-100% "AI-assisted," up from about 40% in February. "AI-assisted" is looser than "authored." Internal tool Forge. Agent counts per engineer: UNVERIFIED.
- Shopify (secondary): in-house agent River; 75% of employees use it (May 2026 presentation, as reported). No Shopify code-share figure found.

### Gaps
- Uber migration numbers (primary), Shopify code share, and Coinbase audit: not found.

**Implication for factory architecture:** uReview's 75%/65%/51% set is a usable template: report "useful" and "addressed" rates for our Gate reviewer, with the human baseline next to it.

## 6. Solo and small-team agent factories

### Takeaway
These projects are open-source and their claims are checkable in repos. Gas Town is the closest to our architecture: named roles, git-backed state, a merge queue with gates.

### Cited findings
- Gas Town [fetched GitHub README, no date or version shown]: Mayor coordinates; Polecats are workers with "persistent identity but ephemeral sessions"; one Witness and one Refinery per rig; Deacon patrols across rigs. Work is beads grouped into convoys. The Refinery is "a Bors-style merge queue — polecats never push directly to main," and bisects a failed batch. Agent state lives in git-backed hooks, "Git worktree-based persistent storage." Scale: "Scale comfortably to 20-30 agents"; "4-10 agents become chaotic" without it. Source: [github.com/steveyegge/gastown](https://github.com/steveyegge/gastown).
- Beads [fetched README]: "distributed graph issue tracker for AI coding agents," built on Dolt; `bd ready` lists unblocked work; `bd update --claim` claims a task atomically; hash IDs avoid merge collisions. About 27.9k stars at fetch. Source: [github.com/steveyegge/beads](https://github.com/steveyegge/beads).
- Superpowers (obra) [fetched README]: seven-stage skill workflow: brainstorming, git worktree setup, plan of 2-5 minute tasks, subagent per task with review after each, TDD, review between tasks ("Critical issues block progress"), finish branch. About 298.6k stars at fetch. Source: [github.com/obra/superpowers](https://github.com/obra/superpowers). Effectiveness: one German tester, 12 sessions, 14% fewer tokens; anecdotal ([secondary](https://www.mejba.me/de/blog/superpowers-plugin-claude-code-review)).
- Mitchell Hashimoto, "My AI Adoption Journey" (2026-02-05) [fetched]: six steps. He runs one agent at a time, not in parallel. Parallel agents are used only for triage and research. No worktrees, task queue or roles are described. Fixes each agent mistake by adding AGENTS.md text or a tool. Numbers: a background agent runs about 10-20% of a workday; deep-mode tasks take 30+ minutes. Source: [mitchellh.com](https://mitchellh.com/writing/my-ai-adoption-journey).

### Gaps
- Real-world run data for Gas Town: not found. Version numbers: not shown on fetched pages.

**Implication for factory architecture:** Gas Town's Refinery (merge queue with gates and bisect on failure) and per-task worktrees are the designs to compare against our Gate and Register steps. Superpowers' "critical issues block progress" between tasks is the same check our Gate does, applied per task rather than per run.
